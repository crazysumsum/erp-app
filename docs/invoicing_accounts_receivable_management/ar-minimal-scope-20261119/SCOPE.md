# 開票與應收：首期最小實作範圍

日期：2026-11-19。作者：`claude-erp-app-tl-01`（Claude側TL）。應PM `61f54f41`第2項。
這是範圍及技術做法的提案，不是實作授權；沒有執行任何東西。來源：`origin/main` `11f42ca3`（只讀）。

**現況**：main上沒有任何開票或應收的程式、資料表或頁面。Sales訂單已保存客戶、幣別、行單價及行金額、付款條款的ID／代碼／名稱（`0073_create_sales_orders.js:10–11`）；Fulfillment已有`SHIPPED`的出貨及出貨行（`0096_create_shipments.js`）。現有44個任務的計劃及其後的R3／R4設計（Exposure、信用警示、歸檔、恢復）**不作為首期依據**。

## 1. 做什麼（四項）

| 功能 | 最小內容 |
| --- | --- |
| 由出貨生成發票 | 選同一客戶、同一幣別的一張或多張`SHIPPED`出貨，建立發票Draft；**整張出貨開票，不拆數量**；一張出貨同一時間只屬於一張未作廢的發票。確認時取號、形成應收。可作廢（須原因），作廢後該出貨可重新開票。 |
| 收款登記 | 客戶、幣別、收款日期、金額、方式、參考號；Draft及確認。 |
| 核銷 | 把已確認的收款核銷到同客戶同幣別的一張或多張已確認發票，可部分核銷；可解除。未核銷的餘額留在收款上。 |
| 帳齡表 | 按客戶及幣別，列出今日的未收額及分桶（未到期、1–30、31–60、61–90、90日以上）；不同幣別不相加。只做現況，不做歷史時點。 |

頁面五個：發票列表及詳情、由出貨建立發票、收款列表及詳情（含核銷）、帳齡表。權限三個：`ar.view`、`ar.invoice.mgmt`、`ar.receipt.mgmt`。

## 2. 不做（列入第二期）

貸項及退款、手動發票、期初匯入、信用額度及Exposure警示、AR關帳日、歷史時點查詢及Statement、CSV匯出、列印版式、歸檔、任何背景工作或恢復任務、出貨沖銷與發票的聯動（見第5節）、容量及效能驗證。

## 3. 技術做法（取最簡單而正確的）

- **一個命令一個交易**。沒有「處理中」狀態，沒有恢復任務；回應遺失時以同一`eventId`重送，由一張操作表（`event_id`唯一）回原結果。做法沿用Purchasing現有的`PurchasingOperationService`。
- **取鎖次序固定**：操作列 → 出貨列（`FOR UPDATE`，ID升序，經Fulfillment提供的讀取介面） → 發票 → 收款 → 核銷 → 編號。開票時在鎖下重驗出貨仍是`SHIPPED`並且沒有其他未作廢的發票。
- **防重開票以資料庫唯一鍵保證**：發票行記錄出貨行ID，未作廢的發票行在該ID上唯一。
- **金額**：沿用Sales的四位小數及BigInt做法。發票行金額按Sam已批准的剩餘池規則，**依出貨的先後次序**計算：同一訂單行的各次出貨依次從剩餘金額及剩餘數量按比例half-up取額，用盡數量的一批取餘數。結果只取決於訂單行及已出貨的數量（都是不會再變的事實），與開票的先後及是否同時開票無關，所以不需要為此加鎖或加表。首期不處理部分取消及關閉訂單對剩餘池的搬移。（2026-11-19更正：原寫「訂單行金額減去已開票的累計」，兩張發票同時開同一訂單行時會算錯尾數，已改。）
- **發票總額的尾數**（Sam 2026-11-19在TL的chat直接決定，原話：「採用 A」；所答的問題：「發票總額尾數：是否採用 A（總額四捨五入到幣別小數位）？」）：發票行金額維持上面的四位小數分攤；**發票總額＝各行金額之和，half-up到該幣別的小數位**。收款及核銷金額只收幣別小數位，所以發票可以收齊。已接受的代價：分批出貨分開開票時，各張發票總額之和可與訂單行金額相差不足一個最小貨幣單位（100.00分三次出貨合計99.99；200.00合計200.01）；只在單價多於幣別小數位或數量有小數時出現。這取代首期對既有BR-014「Invoice Total＝Lines總和」的字面讀法。沒有採用的做法：分攤直接按幣別小數位（幣別小數位可被修改而訂單沒有保存當時的值，而且訂單行金額本身有尾數時仍不收齊）；總額保留四位（尾數收不清）。
- **到期日**：發票日期加付款條款的日數（Sam已決定以發票日期起算）；可改，須原因。
- **未收額**直接存在發票上，核銷及解除時在鎖下更新；帳齡表只讀仍有未收額的發票。不設餘額表及ledger。
- **資料表六張**（確切欄位在開工前另行說明並取得批准，見第6節）：編號、操作、發票、發票行、收款、核銷；Audit沿用現有模組的做法另加一張。
- **跨模組只有一處**：Fulfillment提供一個接呼叫方交易的讀取介面，回出貨、出貨行、訂單行的訂購數量、單價及金額、同一訂單行較早出貨的數量（供上述金額計算）、付款條款。AR不直接查Sales或Fulfillment的表，也不鎖Sales的列。

### 3.1 開票讀取介面的鎖序契約（2026-11-19補入）

兩位TL的統一裁定：Claude側TL提出（agentmsg `7ca92d86`），Codex側TL同意（PM agentmsg `9dc96693`的轉述，作者沒有看到原訊息）。Fulfillment、Sales及AR各自在下一個變更PR記一行引用本節，不另開文件PR。

- **介面**：Fulfillment提供`readInvoiceSourcesInTransaction(tx,{shipmentIds})`，在呼叫方（AR）的READ COMMITTED交易內執行，沿用既有20秒交易時限。
- **只鎖出貨層**：`shipments`列`FOR UPDATE`，主鍵升序；其後出貨行主鍵升序。Sales一側的事實（訂單的幣別及付款條款ID／代碼／名稱、訂單行的訂購數量、單價、行金額）在取得出貨鎖**之後**以非鎖定讀取取得。reader及AR都不主動取任何Sales鎖，所以不與「Sales→Fulfillment／Shipment」的寫入者形成倒序。
- **依據**：已有`SHIPPED`出貨的訂單，上述Sales欄位沒有可執行的寫入者（`origin/main` `11f42ca3`：`SalesOrderService.js:88`只限DRAFT；`SalesOrderLifecycleService.js:106`有履約歷史即不可撤回確認；`SalesFulfillmentService.js:444`、`SalesBackorderService.js:109`、`SalesOrderLifecycleService.js:112`只改數量及version）。不可變性靠service規則而非trigger，以下面兩項補強。
- **補強一（Fulfillment）**：reader在出貨鎖下重驗訂單不是`DRAFT`，並且存在該出貨`confirmation_event_id`對應的`FULFILLMENT_CONFIRM`歷史列。
- **補強二（Sales）**：以一個測試釘住「有履約歷史後，幣別、付款條款、行單價、行金額及訂購數量不可寫」。
- **出貨次序**：同一訂單按`sales_order_status_history`的`FULFILLMENT_CONFIRM.sequence_no`，以`shipment.confirmation_event_id`接合；不用出貨ID或`shipped_at`。
- **驗證及有界**：鎖後重驗每張出貨為`SHIPPED`、行齊全、訂單行歸屬、全部出貨同一客戶及同一幣別；任何不符整批拋錯，不回部分結果。一張發票最多20張出貨（AR在呼叫前檢查）。較早出貨的數量以每個訂單行的最大目標sequence為cutoff；整批來源歷史最多4,000、回傳的較早出貨關聯最多2,000，超限整批fail closed。
- **已知效果**：`ar_invoice_lines`對`sales_orders`／`sales_order_lines`的外鍵，令插入發票行時InnoDB對被引用的Sales列取共享鎖，這發生在出貨鎖之後。AR開的只是已`SHIPPED`的出貨，Sales對該出貨的寫入已完成；若仍遇死結，由InnoDB偵測，AR按現有做法回409，使用者重試。
- **前提**：首期不開放公開的出貨沖銷（Sam 2026-11-19）。其後若開放，「有未作廢發票的出貨不可沖銷」是另一項改動。

## 5. 需要PM決定或協調的事（開工前）

1. **出貨沖銷**：若首期同時開放出貨沖銷，須加一條規則「有未作廢發票的出貨不可沖銷」，並由Fulfillment在沖銷時回查AR。我的建議是首期不開放沖銷（見沖銷裁定），這一項即不需要。
2. **金額分攤放在哪裡**：已批准的設計把剩餘池放在Sales（出貨時定額並保存）。最小做法是開票時由AR按出貨次序重算同一結果，不在Sales加資料；與已批准規則的差別只在首期不處理部分取消及關閉訂單的搬移。PM已於`6e4a0acc`接受由AR在開票時計算，並把「剩餘池移回Sales」列入第二期。
3. **付款條款的日數**：訂單只保存條款的ID、代碼及名稱，沒有保存當時的日數。最小做法是開票時讀該條款現行的日數；這與評審者「不可用現行設定推算舊值」的裁定不同。請確認首期可接受，或由Sales在確認訂單時加存日數。
4. **由誰實作**：main上沒有AR模組，也沒有任命的實作負責人。
