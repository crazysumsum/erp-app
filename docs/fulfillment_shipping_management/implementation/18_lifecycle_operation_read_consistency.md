Status: DECISION_REQUIRED. This is a concrete proposal, not actual human adoption. Task011 production exception remains blocked; unrelated approved implementation/verification may continue. ## Context and observed evidence

Existing Sales lifecycle calls the Fulfillment guard after holding its Sales Order/Lines/mapping locks. Existing Sales transaction isolation stays REPEATABLE READ; HD010 only authorizes new Fulfillment write transactions to use READ COMMITTED. A plain operation lookup can therefore retain an earlier snapshot and falsely report no pending operation. A waiting operation row read can deadlock with PhaseB which acquired operation first and now waits on Sales. DES007/Design§2.8 strictly says operation/lease→Sales→Fulfillment→Shipment/Reversal→providers, and the approved plan requires human disposition of lock-order conflicts; this new read-only lock exception is not covered merely by completeP0 authority.

## A — recommended narrow readiness exception

Only `FulfillmentOpenMatterService.assertSalesLifecycleAllowedInTransaction` may inspect existing owned Fulfillment/Shipment target operations after the caller's Sales and document roots with `FOR SHARE NOWAIT`. It must never claim/insert/takeover/renew/upgrade an operation, wait for it, perform Inventory release or continue after an uncertain read. It retains the read lock until the enclosing Sales transaction ends, so this is explicitly a narrow exception to the strict general acquisition sequence; it does not redefine it for business writers.

Matching IN_PROGRESS means OPEN. ER_LOCK_NOWAIT, missing/incompatible schema, failed probe or any unknown dependency means UNKNOWN. The existing Sales guard must then fail503 and end/rollback the whole transaction before any Inventory release or other lifecycle business effect. This is not a retry loop, timeout increase, successful CLOSED fallback, separate external read or nested transaction. Fresh sales.view+sales.mgmt and fixed WITHDRAW/CANCEL/CLOSE_REMAINING purpose remain required. No Fulfillment permission is imposed on Sales users. All actual domain writers retain operation→Sales→Fulfillment→Shipment/Reversal→providers, current CAS, exact membership, quantities, atomicity and the unchanged Sales/default isolation.

Scope is the already approved Task011 Fulfillment lock/lifecycle core, exact thin DI wrapper and tests. No Sales source, global DB strategy, schema table, lease semantics, route/job/UI or live deployment is added. Before DONE/fullP0, prove genuine Sales→Fulfillment→Inventory lifecycle behavior for CLOSED and active claim/operation/UNKNOWN/missing-provider; RR current membership and the operation/Sales two-connection contention with actual provider/guard; true same-SO/new-child and two-SO/shared-Warehouse lock behavior; complete independent review and all original P0/native/coverage/currentCI gates. Probes alone do not waive those gates.

Trade-off: transient operation contention conservatively returns existing dependency503 and requires retry after the other transaction settles. Correctness and rollback take priority over temporarily accepting a lifecycle release. Baseline-bound adopted spec language must distinguish this nonwaiting readiness inspection from operation ownership/business mutation locks; no broad exception is implied.

## B — retain strict acquisition sequence and redesign preflight

Do not allow the post-Sales operation lock. Rework Sales lifecycle to discover/prelock the complete owned operation scope before acquiring Sales, revalidate after root locks and coordinate newly appearing operations without stale absence. This is a broader Sales/Fulfillment provider contract and implementation change requiring its own reviewed design, exact owner contribution and additional races/recovery evidence. It delays Task011/P0 and is unnecessary if the narrow fail-closed NOWAIT inspection is acceptable. A separate autocommit/connection read or changing existing Sales isolation is not silently authorized as a shortcut.

## Decision boundary
