# HD013 proposal — lifecycle root membership and Warehouse FK gap locks

Status: DECISION_REQUIRED proposal; no change to Sales transaction isolation or Inventory lock strategy has been adopted. HD012 A remains adopted for operation readiness, but does not resolve this distinct root-range issue. Task011/fullP0/PR remain unfinished.

## Observed root cause

Separate reviewer `/root/fulfillment_independent_review` used actual owned MySQL26.7.0 and reproduced the same deadlock with both an empty Fulfillment table and an existing first Order's root. A locks Sales1 and current-reads Fulfillment roots by `(sales_order_id,id)` under RR. B locks Sales2 and starts its first Fulfillment header INSERT. Actual performance_schema shows B holds the shared Warehouse primary-record FK lock while waiting for X INSERT_INTENTION on the root owner-index supremum gap. A then needs Warehouse X to release its Sales reservation and receives ER_LOCK_DEADLOCK. The failed correctness observation must not be called a successful no-deadlock test. No live/shared database was involved.

A covering root index alone cannot remove RR next-key/gap locking. HD012 operation NOWAIT cannot release root gaps acquired earlier, and root NOWAIT still retains those gaps while a later insert starts. Child primary-key reads plus aggregate version witnesses avoid child range gaps but cannot solve the first current root enumeration. Plain RR root enumeration may miss roots committed after the actor opened its read view. Existing version fields alone are not evidence that new Fulfillment roots bump Sales.version; no such cross-owner write is currently implemented or assumed.

## A — recommended localized Sales lifecycle RC

Only SalesOrderLifecycleService's WITHDRAW/CANCEL/CLOSE_REMAINING transactions explicitly request READ COMMITTED through the existing Database service option. Global Database default and all other Sales workflows remain unchanged. No framework isolation implementation, quantity, permission, event, FK/unique/trigger, CAS, rollback or acceptance threshold changes.

The minimum Fulfillment lifecycle provider requires trusted actual active-RC metadata and current request actor, fresh sales.view+sales.mgmt and fixed lifecycle purpose. The caller holds Sales root first; all Fulfillment domain writers must hold that same Sales root before creating/deleting/changing owned work. At each level the guard first holds the actual direct FK/business parent (Sales before Fulfillment, Fulfillment and Lines before Claims/Allocations, Fulfillment before Shipment, Shipment before its Lines/Reversals); Sales root alone is not claimed to stabilize every child against arbitrary writers. Plain RC full root/child ID discovery is therefore current and stable under those held parents; exact sorted primary-ID current row locks revalidate ownership and every state/counter. It takes no owner-range locking read or speculative parent-version witness. Missing/wrong transaction metadata/schema/provider, membership mismatch or other uncertainty returns UNKNOWN and the whole Sales transaction503/rolls back before Inventory release. HD012's operation FOR SHARE NOWAIT remains the only post-domain operation readiness exception, with IN_PROGRESS OPEN and contention UNKNOWN.

Trade-off: this explicitly broadens HD010's localized consistency strategy to an existing named Sales lifecycle flow. It is a material transaction-semantics decision requiring actual human adoption; 'default remains RR' does not pretend existing-flow RC was already approved. RC permits statement-to-statement nonrepeatable reads, so correctness must continue to come from operation/Sales/document/Inventory parent locks, exact-set/current CAS, verified provider outcomes and atomic rollback, not old snapshots. Existing Sales actor and Sales projection tests must be rerun under the actual localized setting, including the former RR snapshot-drift negative case whose RC result now sees current data.

Before adoption/source completion: independently prove early snapshot/new-root visibility and the same two-SO/shared-Warehouse insertion with actual RC current discovery plus sorted primary locks and Inventory writer. After adoption: actual complete lifecycle CLOSED release/replay, OPEN active claim/operation, missing/wrong provider/RC metadata/UNKNOWN, operation-first/Sales contention full rollback, two-SO/shared-Warehouse, child insert/state changes, real default/off and enabled/all-node DI probes, all P0 native/coverage/full developer gates and final independent review. No gate is waived by a candidate probe.

## B — retain Sales RR; Inventory-owned nonwaiting release

Keep the RR root current locking read and its gap locks; modify the existing Inventory owner so only the fixed Sales lifecycle ALL_OUTSTANDING release purpose takes its existing Warehouse lock NOWAIT, after the Inventory operation claim. A Warehouse FK S conflict must immediately reject the whole Sales transaction and release the root gap, allowing the other Order's insert to finish. This avoids waiting through the demonstrated Warehouse cycle without reversing lock order, but changes an existing Inventory owner contract and causes additional conservative retry failures. It needs exact purpose scoping, stable error mapping, whole-transaction rollback/operation cleanup, Inventory owner coordination and native proof. HD012 operation-readiness-only approval does not cover it. It is viable but spreads the fix across an additional owner and retains RR witness complexity.

A broader third alternative adds a Sales-owned collection/version contract to every Fulfillment root membership writer or redesigns operation/auth/Sales preflight before the first RR snapshot. That is more source and cross-owner coordination than either option above, with no implemented consumer proof today.
