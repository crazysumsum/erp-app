## Concrete conflict and native failures

Sales requirement FR-LIFE-001 (`docs/sales_order_management/01_requirement_spec.md`, §8.4) allows a zero-Fulfilled CONFIRMED Order to return to Draft for correction; FR-LIFE-003 allows reconfirmation with new reservations. Sales Design§7.6 explicitly deletes terminal Reservation mappings on withdrawal. SalesOrderService Draft update deletes/recreates Sales Lines. Fulfillment Design§6.5 currently blocks active work, not all historical work; approved0093 retains `fk_ful_claim_mapping` RESTRICT to Sales mapping and `fk_ful_line_source` RESTRICT to SalesLine/Order. Cancelled Fulfillment history must remain immutable and linked. No existing authority was found that forbids withdrawing all Orders with terminal Fulfillment history.

Actual independent reviewer `/root/fulfillment_independent_review` inspected these connected canonical/source paths and confirmed the conflict. Root then fixed two native regressions under the existing desired behavior, both RED,0SKIP in `server/test/integration/fulfillmentWithdrawalHistory.integration.test.js`, private raw log `/private/tmp/fulfillment-p0-task011-withdrawal-history-red-r1.log` (raw SQL/stack is not exported into repo):

1. A zero-Fulfilled Confirmed Order, CANCELLED Fulfillment and terminal CANCELLED/released Claim has no active work. Real lifecycle guard returns CLOSED and Inventory release runs, but withdrawal's mapping DELETE fails actual FK1451. Whole transaction rolls back; no successful withdrawal.
2. Without any Claim, the same cancelled Fulfillment's Line still references SalesLine. Real withdrawal succeeds, but a subsequent real Draft edit fails FK1451 at `DELETE FROM sales_order_lines`. This traps the promised editable Draft, so keeping mappings alone does not solve the problem.

Synthetic starting history is explicitly a fixture of valid persisted FK relationships, not an implementation/sign-off of P1 cancellation or P2 issue. Actual Sales lifecycle, Inventory release, Draft-save service and native FK enforcement are used for the failures. Neither dropping these FKs/deleting history, pretending terminal history is active work, nor swallowing a SQL error as success is acceptable.

## A — recommended explicit withdrawal-only history restriction

Refine Sales FR-LIFE-001/003 and matching Fulfillment lifecycle contract: once any active or archived Fulfillment history exists for an Order, it cannot WITHDRAW back to Draft, even if fulfilled=0 and all Fulfillment work was cancelled/released. This is a real product limitation requiring Sam approval. It does not redefine every terminal row as open work: CANCEL and CLOSE_REMAINING continue to judge actual active work/Claims/Allocations/operations, and retain their current successful terminal-history behavior. Withdrawal with no Fulfillment history remains fully supported, including release, Draft edit and reconfirmation.

The real provider checks owned current/history existence under the held Sales parent before any release; a specific bounded reason `FULFILLMENT_HISTORY_BLOCKS_WITHDRAWAL` is conveyed only for fixed WITHDRAW purpose. The Sales guard maps that exact purpose/reason to a stable409 with clear Chinese recovery guidance, e.g. this Order has Fulfillment history and cannot return to Draft; settle unfinished work, cancel the unfulfilled Order and create a corrected Order. Existing OPEN/UNKNOWN behavior remains for other conditions; unknown/missing required schema/provider still503/whole transaction rollback. No caller flag bypasses the history check. No new route/menu, duplication API, P1/P2 writer, FK weakening or historical unlink is added. The provider keeps its truthful OPEN/CLOSED/UNKNOWN readiness status; terminal history is not relabelled OPEN. A bounded reasonCodes member accompanies a known OPEN/CLOSED result for WITHDRAW, and the Sales guard checks this exact reason/purpose before its ordinary status handling. UNKNOWN still takes precedence and cannot be converted into business eligibility. The exact provider reason result/guard/error handling must receive source/native review after adoption; this proposal does not claim it is implemented.

History means actual owned rows in active tables and the archive mirrors, not a cached boolean; valid parent-owned Archive lifecycle prevents legitimate return to Confirmed after parent archival, but a retained archive row is still conservatively recognized. Missing required history footprint is UNKNOWN, never absence. All existing permission, event/CAS, current-RC, sorted primary locks, HD012 NOWAIT, append-only facts and P0 verification thresholds remain required.

Trade-off: users must cancel and create a corrected Order rather than edit the original after any Fulfillment history. Original business reference/history stays intact, with a clear early409 instead of a late FK500 or an unusable Draft. The change is narrow but intentionally reduces the previously written withdrawal eligibility.

## B — retain withdrawal eligibility with versioned Sales generations

Preserve original FR-LIFE-001 even after terminal Fulfillment work by adding an explicitly Sales-owned immutable Line/Reservation/confirmation-generation model and corresponding Fulfillment routing to those historical generations. Draft edits and reconfirmation must create fresh current identities while old references/snapshots remain addressable; keep consistent quantity/replay/Archive/Export/Audit/provider behavior across generations. Merely retaining old mapping rows fails the second native regression and reconfirmation semantics. This is a materially larger cross-owner design/schema/consumer/history migration change and delays the P0 boundary. Do not implement a partial generation scheme or detach old facts silently.
