# HD-017 — Full DRAFT replacement needs an explicit pending-update contract

Status: ADOPTED A by actual direct user reply on 2026-10-23; implementation and validation in progress. TASK013 is committed687b4db9e1a9f7ffc4124cb9efab740869c758ca; TASK014 inquiry/list work can continue independently. No new mode is implemented or assumed approved.

## Observed current contract mismatch

Approved TASK014 / DES002 requires complete replacement of selected DRAFT lines and atomic Claim delta under all affected Sales/mapping/aggregate locks. This includes adding a previously unselected SO line, switching to a newly available Reservation, and completely replacing the prior selected lines. Real Claim IDs for newly selected sources do not exist before the required capacity proof; early inserts or fabricated IDs would violate the approved sequencing/identity rules.

The delivered Sales CLAIM contract without claimMode strictly requires positive persisted claimId; its all-zero memberless source scope is rejected. HD016 A explicitly approved only PENDING_CREATE for new Fulfillment creation and retained the old persisted-DRAFT path. Delivered FulfillmentLockService.lockClaimCapacityInTransaction also requires the unchanged complete own line set and existing positive fulfillmentLineIds, so it cannot express new selected lines before persistence.

Actual isolated executable probe `/private/tmp/fulfillment-p1-task014-contract-probe.mjs` and its output `/private/tmp/fulfillment-p1-task014-contract-probe.log` confirmed: valid persisted CLAIM accepted; a newly desired null Claim rejected; explicit PENDING_UPDATE rejected; all-zero source-only lock rejected. This is a delivered-interface probe, not a claim that a production Update route/native transaction already exists or failed. Relevant exact current sources are SalesFulfillmentService.js and FulfillmentLockService.js at687b4db9.

Do not use an unrelated existing Claim as a dummy positive identity to force a different final desired set through an old receipt/hash scope. A source read scope must explicitly describe its meaning; no mixed identity or changed-intent second call in one transaction.

## Option A — strict pending-update desired-capacity variant (recommended)

Add CLAIM-only exact `claimMode:"PENDING_UPDATE"` alongside the adopted PENDING_CREATE, with every desired member explicitly claimId:null (no mixed positive/null identities). The new mode is only a read/lock/capacity protocol for desired membership under an existing DRAFT, never a persisted identity or Shipment/apply receipt. Persisted CLAIM without mode, PENDING_CREATE, Shipment/Reverse wire/hash/CAS/receipt semantics remain unchanged.

The Fulfillment update owner takes operation first; discovers routing and all affected old/new Sales line IDs without treating them as proof; binds the current Sales root/line/mapping versions; locks Sales and every existing Fulfillment root/Line/Claim in the approved order; verifies target DRAFT and expected aggregate version; then proves complete actual Item/Inventory/source/counter/active-Claim capacity before private changes. Include removed old lines in affected source scope with zero desired quantity; they still contribute every old active Claim and source/counter to the locked influence proof and must never be filtered away for having desired zero. The complete old/new influence set is not limited by the desired50-per-line/5000-member command bound. total desired remains positive and at most100 selected lines/5000 members, each line at most50. Final mapping-ID distribution excludes the target's replaced active Claims when calculating other documents' capacity, while validating the complete original/current active set and every influencing source. Do not temporarily release capacity to other transactions.

Apply the desired replacement atomically after proof under the existing DES3.4 DRAFT zero-stock-effect projection rebuild policy. Keep Header identity, original CREATE/UPDATE durable outcomes, append-only status History and Audit. Old DRAFT Line/Claim projections may be deleted and rebuilt; they are not immutable business posting history. Do not promise to retain every removed Line/Claim ID or released row. Before rebuilding, verify target DRAFT, no Allocation/Pick/Shipment/posting history or corresponding effects, and all original current Claim/counter/source invariants; unexpected references/state fail closed and roll back. New real Line/Claim IDs are created only after proof, in the same transaction with audit and outcome. Do not alter any already posted, allocated, picked, shipped, archived or append-only history rows. This is the already specified DRAFT rebuild policy, not a new tombstone schema or a reduction of history retention. Root version CAS, same-event result, all-or-nothing rollback, original 20-second timeout, NFRs and complete P0/P1 gates remain. An exact update helper owns target identity/status/CAS; callers cannot turn a pending read into Inventory allocation/post authority.

Narrow shared scope is SalesFulfillmentService.js, existing focused Sales provider tests, FulfillmentLockService/Service and planned update handlers/tests, existing read-only Inventory owner capacity entry point without a new Inventory write API, and corresponding Fulfillment/Sales canonical contract pins. Sales owner coordination and actual owner review are required. The actual trusted active RC transaction and fresh actor are mandatory; wrong isolation or fabricated context fail before claims/effects. No schema/migration, global isolation, business eligibility, allocation order, write authorization, phase boundary or P2 operation routing change.

## Option B — separate Sales source-scope locking API

Keep CLAIM variants unchanged and add a separate Sales-owned pure source-scope read/locking method with explicit current projection and no Claim identity. Fulfillment still must implement the same complete existing-DRAFT capacity, exact membership, quantity delta, CAS, lock order and atomic rollback. This avoids another CLAIM mode but creates a separate public owner API/DTO, integration and regression surface. It needs the same owner review and native matrix; it does not solve the mismatch by itself.

## Trade-off and default

A reuses the already reviewed pending capacity machinery while giving the desired-update read scope an explicit distinct identity. B separates concerns more visibly but duplicates an owner surface. Recommend A with strict negative tests and complete source proof; do not adopt A merely because it is the default recommendation. Await actual human selection. No restriction of the approved full-replace feature and no weakening of tests/timeout is proposed.
