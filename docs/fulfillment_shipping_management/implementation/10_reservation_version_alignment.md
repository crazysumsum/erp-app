## A — Explicit last-sync/current-CAS separation and narrow cadence refinement (recommended)

No new schema, payload field, permission or Sales synchronization write endpoint. Sales `CLAIM` intent member.expectedVersion remains the Sales projection's last-synchronized Inventory version, obtained from the locked Sales projection, with strict equality to its mapping. This is a Sales CAS and does not assert current Inventory truth. The separate Inventory command expectedVersion and Fulfillment Claim.inventory_version come from a named Inventory-owned current-state projection in the same transaction. Create/Update must lock/revalidate native Reservation scope/source/status/current counters in the approved owner lock order and enforce the sum of all active Fulfillment Claims≤actual Inventory outstanding; a stale Sales quantity projection or caller flag cannot stand in for this proof.

Allocation/Release/Reallocate which change only Allocation/Balance holds and Reservation CAS, leaving original/consumed/released/outstanding quantities/status unchanged, may leave Sales last-sync version behind. This is an explicit narrow refinement of Sales§4.10's per-update refresh sentence and wire04, subject to actual Sam adoption and Sales owner coordination. It is not a general waiver for quantity-changing Inventory updates. All quantity-changing Sales/Fulfillment events still synchronize projections atomically from verified owner outcomes; generic external drift remains a reconciliation/refusal condition.

For Shipment Confirm/Reverse, intent member.expectedVersion is the Inventory current CAS. Sales lock rejects values below mapping last-sync rather than demanding equality. A greater version is merely an early bound, never evidence that intervening changes were quantity-neutral. Actual owner effects must perform exact current-version CAS; Sales apply must consume the same active-RC transaction's unforgeable owner receipt, action/event/shipment/requestHash/full exact members, result.expectedVersion=intent current, actual result.version=current+1 and native current Reservation.version=result.version. All four native counters and status must equal the locked mapping before±the exact Issue/Restore quantity; foreign source/original identity and any unexplained counter drift reject and roll back both owners. Sales UPDATE still uses the unchanged old mapping last-sync version in WHERE CAS and sets the verified actual new version. Original Sales reserve operation/event identities remain immutable, with all0078/0086 triggers unchanged.

Completed operation replay returns its persisted original result before rechecking later current versions; no new effect is posted. Reverse uses the original complete Issue/confirmation identity, the current native Reservation version and the same complete counter/source checks. No caller-labelled “version-only” assertion is trusted. Private preclaim/consume, operation-before-domain lock order, parent/root/Warehouse locks, native FK/unique/CAS, rollback and full P0 gates remain mandatory. The database global/default isolation and other module workflows stay unchanged.

Required actual joint tests before0B: Allocate→partialRelease→Reallocate with Sales last-sync unchanged, repeated CLAIM using documented Sales CAS plus actual Inventory current-state/counter proof, Issue+Sales apply to actual current+1, Reverse and later-version original replay. Negative cases cover current<last-sync, stale/future native CAS, changed source/status/counters, lost mapping CAS, wrong/copy/foreign receipt/hash/exact sets, wrong original confirmation/partial Reverse, and late failure after both owners' effects with full rollback. Existing native truth and Inventory receipt verifier must be real, not doubles or fixture mapping synchronization.

Trade-off: smallest owner-aligned implementation; readers must distinguish last-sync observation from current owner CAS. Explicit current-state validation and end-to-end tests carry that distinction. No acceptance, coverage or native transaction budget is reduced.
