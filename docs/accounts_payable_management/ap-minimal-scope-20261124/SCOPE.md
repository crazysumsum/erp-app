## 1. 做什麼

| 功能 | 最小內容 |
| --- | --- |
| 由收貨登記供應商發票 | 選同一供應商、同一幣別的一張或多張`CONFIRMED`收貨（可來自不同採購單），建立發票草稿；**整張收貨開票，不拆數量**（待Sam，決定二）；一張收貨同一時間只屬於一張未作廢、未取消的發票。必須填供應商的發票號碼及發票日期；同一供應商下，有效發票的供應商發票號碼不可重複。確認時取內部號碼、形成應付。草稿可取消；已確認的可作廢（須原因，須先解除核銷），作廢後收貨可重新開票。 |
| 金額與供應商發票對齊（待Sam，決定一） | 行金額預設按採購單價算出；具專屬權限者可把行金額改為供應商發票上該行的金額並填原因，系統同時保存按採購單價算出的金額。可加費用行（描述、正數金額）記錄同一張發票上的運費等收費。只有費用行的發票即「無採購單發票」，須填原因。確認時必須已輸入供應商發票總額，並且與系統算出的總額完全相等。對不齊的發票留在草稿，不可以用虛構的費用湊數（限制見`DECISIONS.md`決定一）。 |
| 付款登記 | 供應商、幣別、付款日期、金額、方式、參考號；草稿、確認、取消、作廢（須原因，須先解除核銷）。只記錄已發生的付款；不記錄公司出款帳戶，不讀供應商銀行資料。 |
| 核銷及解除 | 把已確認的付款核銷到同供應商同幣別的一張或多張已確認發票，可部分核銷；可解除。未核銷的餘額留在付款上（即預付款），日後可再核銷。 |
| 應付帳齡表 | 按供應商及幣別列出今日的未付額及分桶（未到期、1–30、31–60、61–90、90日以上）；不同幣別不相加。只做現況。 |

頁面七個，與應收一一對應：發票列表、發票詳情（含草稿修改）、建立發票（由收貨，或無採購單）、付款列表、建立付款、付款詳情（含核銷）、帳齡表。
權限：`ap.view`、`ap.invoice.mgmt`、`ap.payment.mgmt`；決定一採A時另加`ap.invoice.price.override`。入帳與付款由不同權限控制。新權限照`0125`的做法授予系統管理員。

## 3. 技術做法（沿用應收已在main上的模式）

- **一個命令一個交易**，沒有「處理中」狀態，沒有恢復任務；回應遺失時以同一`eventId`重送，由操作表（`event_id`唯一）回原結果。直接沿用`server/src/modules/ar/arCommand.js`的做法。
- **命令**：發票——建立、修改草稿、確認、取消、作廢；付款——建立、確認、取消、作廢、核銷、解除核銷。比應收多一個「修改草稿」：供應商發票號碼、到期日、輸入的總額、備註、行金額及原因、費用行（整組取代）；發票日期不可修改（3.3第1項），以版本號防止互相覆蓋，只碰應付自己的表。
- **防重**以資料庫唯一鍵保證：(a) 發票行記錄收貨行ID，未作廢、未取消時在該ID上唯一；(b) 同一供應商的有效發票，其正規化後的供應商發票號碼唯一。正規化由程式做（去首尾空白、轉大寫），存入以`utf8mb4_bin`比較的欄位——期初應收R1（前置空白繞過唯一鍵）的同一教訓。
- **金額**：四位小數、BigInt計算，沿用應收。按採購單價的行金額＝收貨的基本數量 × 採購行單價 ÷ 採購單位換算因子，half-up到四位小數，每行各自計算；整行開票所以沒有分攤尾差。按實際收貨數量計，含超收。發票行金額預設等於它；改為其他金額須專屬權限及原因。**發票總額＝各行金額之和half-up到幣別小數位**（應收已定的規則A）。付款及核銷金額只收幣別小數位。金額欄為`DECIMAL(19,4)`；算出的金額超出範圍時拒絕命令，不截斷。
- **到期日**（按FR-011原規則）：以採購單保存的付款條款快照（`calculationType`、`dueDays`；`PurchaseOrderService.js:437`）及發票日期，用Business Master現有的純函式`calculateDueDate`（`businessMasterRules.js:88`）算出預設值，不讀條款的現行設定。所選收貨的各張採購單，其快照（代碼、計算方式、日數）完全相同才有預設值——只比條款ID不夠；快照不同、沒有條款、條款為`MANUAL`或無採購單發票時必須輸入到期日。改動預設值須填原因。這一點與應收不同（應收讀現行值）。
- **未付額**直接存在發票上，核銷及解除時在鎖下更新；帳齡表只讀仍有未付額的已確認發票。不設餘額表及ledger。
- **供應商狀態**：由收貨開票、付款、核銷、解除及作廢不因供應商其後被停用、封鎖或封存而被擋（債務已存在），這些命令不鎖也不驗供應商狀態。**無採購單發票是新增的債務**，只可開給啟用中的供應商，而且在交易內驗證：建立及確認無採購單發票時，先以`SupplierLookupService.assertUsableInTransaction(tx, supplierId, { purpose: "purchase" })`鎖供應商列並重驗啟用中，再插入或鎖發票（次序：供應商 → 發票）。所以供應商封存之後不能新建無採購單發票；封存前已有的無採購單草稿在供應商不是啟用中的期間不能確認，仍可取消。確認時先以普通讀取取得草稿的供應商ID，鎖供應商後才鎖草稿並重驗供應商ID、狀態及版本；供應商其後若恢復啟用，草稿重驗通過後可以確認（Supplier負責人`db22b63a`確認）。供應商資料只經`SupplierLookupService`讀ID、代碼、名稱及狀態，應付不直接查`suppliers`表。
- **供應商查詢的接口落實**（TL裁定，agentmsg `ae4dfaad`的答覆；r6新增，只是把上一條規則落到接口，不改規則）：建立付款用Supplier新增的`findByIdInTransaction(connection, supplierId, { purpose: "history" })`——在應付的交易內以普通讀取取ID、代碼、名稱，不加鎖、不驗啟用中，找不到即拒絕。清償既有債務的付款不可呼叫`assertUsableInTransaction`（那會多取供應商列的排他鎖，並擋住已停用供應商的付款）；只有預付款才用它，見3.3第3項。由收貨建立發票時，供應商ID及代碼／名稱取自Purchasing reader回傳的收貨資料，不另讀Supplier。無採購單發票的建立及確認用`assertUsableInTransaction`（見上）。其餘命令不讀也不鎖Supplier。這個新方法由Supplier負責人以獨立的小提交交付（暫稱S0），須先於A3合併。
- **Business Master影響檢查**：`ap_invoices`一建立，預留的檢查即回UNKNOWN並擋住所有幣別及付款條款異動，所以`ApBusinessMasterImpactChecker`必須與資料表在同一個PR交付（照`ArBusinessMasterImpactChecker`）。
- **資料表七張**，與應收一一對應：編號、操作、發票、發票行、付款、核銷、操作記錄。欄位見`TABLES.md`；Sam批准前不寫migration。

### 3.1 收貨來源讀取介面及鎖序契約

Purchasing負責人已按main `80b54298`窄核（提案agentmsg `8f4c739f`，回覆`9e2fd7ab`）：本節的介面、鎖序及清單改動在這個範圍內可行，「未見反向鎖路」；這是按來源閱讀的結論，沒有執行。實作排在Sam批准之後。

- **介面**：Purchasing提供`readSupplierInvoiceSourcesInTransaction(tx,{goodsReceiptIds})`，在呼叫方（AP）的READ COMMITTED交易內執行。AP不直接查採購的表。
- **取鎖**：先以普通讀取解析每張收貨所屬的採購單（確認後由trigger凍結）→ `purchase_orders`列`FOR UPDATE`，ID升序 → 採購行 → 收貨表頭`FOR UPDATE`，ID升序 → 收貨行。這是Purchasing現行的次序（`GoodsReceiptService.#lockForReplace`：採購單表頭 → 採購行 → 收貨表頭 → 收貨行 → 明細）。**不採用應收「只鎖來源列」的做法**，理由是與來源模組的次序一致：Purchasing的收貨修改及確認都先取採購單再取收貨（`GoodsReceiptService.js:207`的`#lockForReplace`；另見`GoodsReceiptFacts.js:19`：持有採購單鎖時對該單全部收貨取共享鎖），其負責人（`78e58d3b`、`9e2fd7ab`）及11-18裁定都要求應付取同一個序列化點。收貨草稿的取消（`GoodsReceiptService.js:299`）只鎖收貨表頭、不回頭取採購單：它與reader可能等待同一列收貨表頭的鎖，但取消方不再取採購單，reader鎖後拒絕`DRAFT`及`CANCELLED`，所以只是先後等待（Purchasing負責人`788dae0a`的表述）。我沒有逐一讀過Purchasing的每個寫入者。reader不套用「可收貨的採購單」這個狀態條件，否則已全收或已結案的採購單之下合法的已確認收貨會被漏掉。
- **鎖後重驗（任何不符整批拋錯，不回部分結果）**：收貨→採購單的歸屬沒有變並且都在已鎖的採購單之內；每張收貨`status = CONFIRMED`並且`total_reversed_base_quantity = 0`；全部同一供應商、同一幣別；每張至少一行、不多於100行。一次最多20張收貨。
- **回傳**：每張收貨的ID、單號、收貨日期、供應商ID及代碼／名稱快照、採購單ID及單號、幣別及小數位快照、付款條款ID及快照；每行的收貨行ID、行號、採購行ID、SKU的ID、代碼及名稱快照、基本單位、採購單位、換算因子、收貨基本數量、採購行單價。
- **哪些命令呼叫它**：只有「建立草稿」。建立時在同一交易為每張所選收貨的**全部**收貨行各建一行發票行，不多不少。確認不重讀來源（收貨事實已凍結，首期沒有沖銷入口，應付沒有「發票日期不早於收貨日期」的規則）。取消及作廢在同一交易清掉該發票全部行的唯一鍵欄位，不取採購的鎖、不改來源的外鍵欄位、不回頭讀採購的表：釋放只會減少佔用，不等待任何採購側的鎖，所以不形成環。Purchasing負責人在`78e58d3b`原本要求釋放也共用同一個序列化點；看過本提案後在`9e2fd7ab`接受首期不取，條件即上述兩個「不」。
- **死結及鎖等待逾時**：應付的交易包裝須把兩者對應為可重試的409，不回500（Purchasing負責人`9e2fd7ab`的要求）。整個交易回滾，操作列也不留下，所以使用者可用同一個`eventId`重試；沿用`arCommand.js:128`的對應（`CONCURRENT_OPERATION`）。
- **AP一側的次序**：每個命令先取操作列，最後取編號列。建立草稿：（reader：採購單 → 收貨）→ 新的發票及發票行。修改草稿、確認、取消、作廢發票：只鎖該發票一列及其行；例外是無採購單發票的建立及確認，在發票之前先鎖供應商列（見上面「供應商狀態」）。確認、取消、作廢付款：只鎖該付款一列。核銷及解除：付款列 → 發票列（ID升序）→ 核銷列，即應收現行的次序（`ArReceiptService.js:151`、`:89`、`:126–128`）。**沒有任何命令先鎖發票再鎖付款**：作廢發票及作廢付款都只鎖自己那一列，憑該列上的`allocated_amount`為0判斷沒有有效核銷，不去讀或鎖另一張表，所以不會與「付款 → 發票」反向等待。
- **外鍵**：發票行只對`goods_receipts`、`goods_receipt_lines`宣告外鍵，其中收貨行以複合外鍵（收貨行ID＋收貨ID，對應現有的`uq_gr_lines_id_gr`）保證該行確實屬於該收貨；採購單及採購行只存ID及單號快照，不宣告外鍵（收貨對採購單已有`RESTRICT`外鍵）。發票及付款對`suppliers`、`currencies`的外鍵令插入時取共享鎖，發生在採購單鎖之後，方向是採購單 → 供應商，與確認收貨相同（`GoodsReceiptPostingService.js:31`）；與Supplier管理「供應商 → 採購單」之間是既有的那條邊，沿用現行處理（InnoDB偵測死結，回409重試）。這一項沒有實測。
- **收貨清單**：建立發票頁用現有的`GET /api/v1/goods-receipts`列出`CONFIRMED`收貨，再以應付的端點標示哪些已在發票上（應收的同一做法）。現有清單沒有供應商篩選，回傳沒有幣別；需要Purchasing加`supplierId`篩選及回傳採購單的`currencyCode`（其負責人`9e2fd7ab`接受）。使用者須有`purchasing.view`。「已在發票上」的標示按頁批次讀取，只供顯示；是否可開票以建立草稿的交易內檢查為準。已知限制：清單不能只列「未開票」的收貨（那需要跨模組查詢），與應收相同。
- **前提**：首期沒有收貨沖銷入口。將來開放時，規則是「有未作廢、未取消應付發票的收貨不可沖銷」，由沖銷在採購單鎖下、碰庫存之前查應付；屬另一項改動，屆時連同釋放路徑一併重審。

### 3.2 與11-18裁定的關係

`ap-receiving-contract-ruling-20261118/RULING.md`是為完整版（按數量部分開票、有收貨沖銷）寫的。就最小版本逐節說明：

| 11-18裁定 | 最小版本 |
| --- | --- |
| §1 D8、D9及草稿算佔用 | D9沿用。草稿算佔用沿用（草稿即佔用整張收貨）。D8不觸發：整張開票下未佔用數量為零，而且沒有沖銷入口。 |

### 3.3 實作期間的裁定（r7）

以下是實作期間各負責人提出、由TL裁定的事項；全部不涉及資料表。**狀態：Sam已接受這四項**（2026-11-24）。PM把四項以Decision Required的形式交他（PM `f999ad64`；非作者評審者在`4d3b3949`指出預付款一項是使用者可見的業務收窄）。PM工作階段：問「應付評審期間收窄的四條規則是否都接受？」，答「都接受」（PM `c9185c17`轉述）。TL的chat：問「PM 轉述你答「都接受」（應付評審期間收窄的四條規則），是你的意思嗎？」，答「是我的意思」；提問前作者列出了四條及其後果，包括預付款判斷的已知空隙。接受的範圍只限下列四項的下列說法，不涉及任何資料表。r9相對r8只改了這一段狀態。

1. **草稿的發票日期不可修改**（答apar-01 `47afebde`，裁定`4ed7f369`）。原因：到期日按採購單條款快照計算，而發票表只保存條款的代碼及名稱，修改草稿又不呼叫Purchasing的reader，改了發票日期之後無法重算預設到期日。做法：發票日期在建立草稿時確定；「修改草稿」不可改發票日期，要改就取消草稿重建。「修改草稿」可改到期日：新值不早於發票日期，只要與現存的到期日不同就必須附原因，並把`due_date_overridden`設為1；伺服器不重算、不判斷是否改回預設值。不以操作記錄作計算來源，不加欄位，不回查Purchasing。對使用者可見的後果：發票日期打錯要取消重建，已輸入的行金額調整及費用行須重新輸入。PM `fdd386c0`表示會把這一點知會Sam。
2. **未來日期的發票不可確認**：這是A2的非作者評審加上的規則，原文在評審者的`95427ed1`（A2三項必修之一）及apar-01的`8d703847`（出處由PM `f999ad64`提供；這兩則不是發給我的，我沒有讀過原文，以該兩則為準）。它與需求FR-008「發票日期在未來時拒絕」一致。
3. **付款的供應商資格**（答Supplier `6b1521bf`，裁定`2d376220`；取代我在`f894f91e`內按現時狀態拒絕草稿及待審批供應商的一句）。建立付款及確認付款時都作同一個判斷：先以`findByIdInTransaction`讀供應商（找不到即拒絕）；再查該供應商、該幣別是否有已確認而且未付額大於0的應付發票（普通讀取）。有，即清償既有債務，不論供應商狀態都允許，不鎖不驗；付款金額可以大於未付額。沒有，即預付款，必須以`assertUsableInTransaction(tx, supplierId, { purpose: "purchase" })`鎖供應商列並驗證啟用中，才插入或鎖付款（次序：供應商 → 付款），不是啟用中即拒絕。原因：草稿供應商可以直接封存，現時狀態不能代表曾經核准；預付款是新增的往來，與無採購單發票同一原則。取消、作廢付款、核銷及解除不讀也不鎖供應商。已知而接受的空隙：未付發票的查詢是普通讀取，若在判斷之後、提交之前該發票剛好被另一筆付款核銷完，這筆付款會成為非啟用供應商名下的餘額。
4. **頁面怎樣選供應商**（答apar-01 `f36d59a5`，裁定`f894f91e`）。不為應付另建供應商搜尋的provider或端點。既有債務：由帳齡列、發票詳情或發票列表進入建立付款，供應商及幣別由該列帶入，只需應付自己的權限（應收的同一做法）。新的往來（預付款、無採購單發票、由收貨建立發票時按供應商篩選）：用Supplier現有的清單端點搜尋，使用者須另有`supplier.view`；沒有時頁面不顯示搜尋並提示所需權限。應付的命令只收供應商ID，不要求`supplier.view`。角色配置：入帳人員為`ap.view`、`ap.invoice.mgmt`、`purchasing.view`、`supplier.view`；付款人員為`ap.view`、`ap.payment.mgmt`，要登記預付款的另加`supplier.view`。取捨：`supplier.view`會讓應付人員看到供應商主檔及遮蔽後的銀行帳戶清單（完整帳號另須`supplier.bank.view`）。

第3項令鎖序多了一條「供應商 → 應付付款」（只在預付款的建立及確認），與無採購單發票的「供應商 → 應付發票」同方向，也與Supplier管理的檢查「供應商 → 應付付款 → 應付發票」同方向；沒有新增反向的邊。這是按來源閱讀的結論，沒有執行。

## 6. 沒有做而應該知道的

- **Supplier的引用檢查（待Sam，決定四）**：Supplier在供應商被採購單引用時鎖定其代碼，有未完成的採購單時不准封存，永久刪除前也查引用（`supplierReferenceCheckers.js`；`SupplierAdminService.js:589–594`、`:706–710`、`:790–835`）。應付上線後是否加對應的檢查由Sam決定。建議加（決定四A）：應付提供兩個檢查——「有未付額的已確認發票」擋封存，「任何應付發票或付款」鎖定代碼並令永久刪除回明確的訊息——由Supplier在`createSupplierReferenceServices()`接線，兩邊都不改表。
- **不論決定四選哪一項**：已有的付款、核銷及解除不因供應商狀態受阻；發票及付款保存當時的代碼及名稱。Supplier有受控的永久刪除（只限從未啟用的草稿供應商，`SupplierAdminService.js:790–835`），它已把外鍵拒絕對應為409 `SUPPLIER_REFERENCED`，所以應付的`RESTRICT`外鍵是保底，不會變成未處理的錯誤。（r2寫「Supplier沒有實體刪除供應商的路徑」是錯的：我的搜尋式沒有匹配到`:811`的`DELETE`，Supplier負責人`342421e1`指正。）
- **決定四採A時的鎖序**（按來源閱讀，沒有執行）：Supplier管理先鎖供應商列，然後逐個執行已接線的檢查（採購單的檢查對採購單取`FOR SHARE`），全部在同一個交易內。封存用的檢查只讀`ap_invoices`（已確認而且未付額大於0）；鎖代碼及永久刪除用的檢查要讀兩張表，**固定先`ap_payments`後`ap_invoices`**，都用`FOR SHARE`，與應付核銷「付款 → 發票」的次序一致——若檢查反過來先鎖發票，就會與核銷互相等待。**只承諾兩件事**：供應商列先於所有下游檢查；應付的引用檢查內部是付款 → 發票。採購單的檢查與應付的檢查之間誰先誰後**不作保證**：`SupplierReferenceService.js:10`按檢查的顯示名稱（`localeCompare`）排序，不是按接線的次序（Supplier負責人`db22b63a`指正），本設計不依賴這個先後。理由：Supplier管理從一開始就持有供應商列的排他鎖，而由收貨建立發票的應付交易在持有採購單鎖之後必須因外鍵取供應商的共享鎖，所以兩者一旦交錯，不論採購單的檢查與應付的檢查誰先，都落在下面第(3)條那一類死結上。
- **各條邊的處理**：(1) 無採購單發票的建立及確認先鎖供應商列，與Supplier管理在同一列上排隊，封存與新增無採購單債務之間因此有序列化，不會在封存檢查通過之後才冒出一張新的無採購單發票。(2) 核銷、解除及其餘只改應付列的命令不取供應商；Supplier管理的檢查會等它們的列鎖，它們不等Supplier，這一對之間沒有反向等待。(3) 由收貨建立發票及建立付款在插入時因外鍵對供應商取共享鎖；此時若Supplier管理正持有供應商列並等待採購單或應付的列，可以死結，與現有「採購單 ↔ 供應商」那條邊同一類，兩邊都已把死結對應為可重試的409（`SupplierAdminService.js:750–752`、`arCommand.js:128`）。這裡只列出已知的邊，沒有證明整體無環。
- **封存檢查只是封存當刻的門檻**：封存之後，解除核銷，或為封存前已有的收貨登記及確認發票，仍可令已封存的供應商出現未付額；應付不擋這些操作，因為那是既有的債務。
