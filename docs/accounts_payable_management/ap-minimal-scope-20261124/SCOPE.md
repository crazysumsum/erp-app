## 1. 做什麼

| 功能 | 最小內容 |
| --- | --- |
| 由收貨登記供應商發票 | 選同一供應商、同一幣別的一張或多張`CONFIRMED`收貨（可來自不同採購單），建立發票草稿；**整張收貨開票，不拆數量**（待Sam，決定二）；一張收貨同一時間只屬於一張未作廢、未取消的發票。必須填供應商的發票號碼及發票日期；同一供應商下，有效發票的供應商發票號碼不可重複。確認時取內部號碼、形成應付。草稿可取消；已確認的可作廢（須原因，須先解除核銷），作廢後收貨可重新開票。 |
| 金額與供應商發票對齊（待Sam，決定一） | 行單價預設為採購單價；具專屬權限者可改價並填原因。可加費用行（描述、金額）記錄同一張發票上的運費等收費。只有費用行的發票即「無採購單發票」，須填原因。確認時系統算出的總額必須等於使用者輸入的供應商發票總額。 |
| 付款登記 | 供應商、幣別、付款日期、金額、方式、參考號；草稿、確認、取消、作廢（須原因，須先解除核銷）。只記錄已發生的付款；不記錄公司出款帳戶，不讀供應商銀行資料。 |
| 核銷及解除 | 把已確認的付款核銷到同供應商同幣別的一張或多張已確認發票，可部分核銷；可解除。未核銷的餘額留在付款上（即預付款），日後可再核銷。 |
| 應付帳齡表 | 按供應商及幣別列出今日的未付額及分桶（未到期、1–30、31–60、61–90、90日以上）；不同幣別不相加。只做現況。 |

頁面七個，與應收一一對應：發票列表、發票詳情（含草稿修改）、建立發票（由收貨，或無採購單）、付款列表、建立付款、付款詳情（含核銷）、帳齡表。
權限：`ap.view`、`ap.invoice.mgmt`、`ap.payment.mgmt`；決定一採A時另加`ap.invoice.price.override`。入帳與付款由不同權限控制。新權限照`0125`的做法授予系統管理員。

## 3. 技術做法（沿用應收已在main上的模式）

- **一個命令一個交易**，沒有「處理中」狀態，沒有恢復任務；回應遺失時以同一`eventId`重送，由操作表（`event_id`唯一）回原結果。直接沿用`server/src/modules/ar/arCommand.js`的做法。
- **命令**：發票——建立、修改草稿、確認、取消、作廢；付款——建立、確認、取消、作廢、核銷、解除核銷。比應收多一個「修改草稿」：供應商發票號碼、日期、到期日、輸入的總額、備註、行單價及原因、費用行（整組取代），以版本號防止互相覆蓋，只碰應付自己的表。
- **防重**以資料庫唯一鍵保證：(a) 發票行記錄收貨行ID，未作廢、未取消時在該ID上唯一；(b) 同一供應商的有效發票，其正規化後的供應商發票號碼唯一。正規化由程式做（去首尾空白、轉大寫），存入以`utf8mb4_bin`比較的欄位——期初應收R1（前置空白繞過唯一鍵）的同一教訓。
- **金額**：四位小數、BigInt計算，沿用應收。收貨行金額＝收貨的基本數量 × 行單價 ÷ 採購單位換算因子，half-up到四位小數，每行各自計算；整行開票所以沒有分攤尾差。按實際收貨數量計，含超收。**發票總額＝各行金額之和half-up到幣別小數位**（應收已定的規則A）。付款及核銷金額只收幣別小數位。金額欄為`DECIMAL(19,4)`；算出的金額超出範圍時拒絕命令，不截斷。
- **到期日**：與應收相同——發票日期按採購單的付款條款（以條款ID讀Business Master現行的計算方式）算出預設值；所選收貨的條款不同或沒有條款時必須輸入；改動預設值須填原因。開票時寫入發票，其後條款改動不影響。（與完整版FR-011「按採購單快照計算」的差別只在讀現行值而非快照；使用者可改。）
- **未付額**直接存在發票上，核銷及解除時在鎖下更新；帳齡表只讀仍有未付額的已確認發票。不設餘額表及ledger。
- **供應商狀態**：由收貨開票及付款不因供應商其後被停用而被擋（債務已存在）；無採購單發票只可開給啟用中的供應商。供應商資料只經`SupplierLookupService`讀ID、代碼、名稱及狀態。
- **Business Master影響檢查**：`ap_invoices`一建立，預留的檢查即回UNKNOWN並擋住所有幣別及付款條款異動，所以`ApBusinessMasterImpactChecker`必須與資料表在同一個PR交付（照`ArBusinessMasterImpactChecker`）。
- **資料表七張**，與應收一一對應：編號、操作、發票、發票行、付款、核銷、操作記錄。欄位見`TABLES.md`；Sam批准前不寫migration。

### 3.1 收貨來源讀取介面及鎖序契約

Purchasing負責人已按main `80b54298`窄核（提案agentmsg `8f4c739f`，回覆`9e2fd7ab`）：本節的介面、鎖序及清單改動在這個範圍內可行，「未見反向鎖路」；這是按來源閱讀的結論，沒有執行。實作排在Sam批准之後。

- **介面**：Purchasing提供`readSupplierInvoiceSourcesInTransaction(tx,{goodsReceiptIds})`，在呼叫方（AP）的READ COMMITTED交易內執行。AP不直接查採購的表。
- **取鎖**：先以普通讀取解析每張收貨所屬的採購單（確認後由trigger凍結）→ `purchase_orders`列`FOR UPDATE`，ID升序 → 採購行 → 收貨表頭`FOR UPDATE`，ID升序 → 收貨行。這是Purchasing現行的次序（`GoodsReceiptService.#lockForReplace`：採購單表頭 → 採購行 → 收貨表頭 → 收貨行 → 明細）。**不採用應收「只鎖來源列」的做法**，理由是與來源模組的次序一致：Purchasing的收貨修改及確認都先取採購單再取收貨（`GoodsReceiptService.js:38–40`；另見`GoodsReceiptFacts.js:19`：持有採購單鎖時對該單全部收貨取共享鎖），其負責人（`78e58d3b`、`9e2fd7ab`）及11-18裁定都要求應付取同一個序列化點。收貨草稿的取消只鎖收貨、不回頭取採購單（`9e2fd7ab`）；它只處理草稿，而reader鎖後只接受`CONFIRMED`，兩者不交錯。我沒有逐一讀過Purchasing的每個寫入者。reader不套用「可收貨的採購單」這個狀態條件，否則已全收或已結案的採購單之下合法的已確認收貨會被漏掉。
- **鎖後重驗（任何不符整批拋錯，不回部分結果）**：收貨→採購單的歸屬沒有變並且都在已鎖的採購單之內；每張收貨`status = CONFIRMED`並且`total_reversed_base_quantity = 0`；全部同一供應商、同一幣別；每張至少一行、不多於100行。一次最多20張收貨。
- **回傳**：每張收貨的ID、單號、收貨日期、供應商ID及代碼／名稱快照、採購單ID及單號、幣別及小數位快照、付款條款ID及快照；每行的收貨行ID、行號、採購行ID、SKU代碼及名稱快照、基本單位、採購單位、換算因子、收貨基本數量、採購行單價。
- **哪些命令呼叫它**：只有「建立草稿」。建立時在同一交易為每張所選收貨的**全部**收貨行各建一行發票行，不多不少。確認不重讀來源（收貨事實已凍結，首期沒有沖銷入口，應付沒有「發票日期不早於收貨日期」的規則）。取消及作廢在同一交易清掉該發票全部行的唯一鍵欄位，不取採購的鎖、不改來源的外鍵欄位、不回頭讀採購的表：釋放只會減少佔用，不等待任何採購側的鎖，所以不形成環。Purchasing負責人在`78e58d3b`原本要求釋放也共用同一個序列化點；看過本提案後在`9e2fd7ab`接受首期不取，條件即上述兩個「不」。
- **死結及鎖等待逾時**：應付的交易包裝須把兩者對應為可重試的409，不回500（Purchasing負責人`9e2fd7ab`的要求）。
- **AP一側的次序**：操作列 →（reader：採購單 → 收貨）→ 發票 → 付款 → 核銷 → 編號。核銷時付款列先於發票列，發票列ID升序。
- **外鍵**：發票行只對`goods_receipts`、`goods_receipt_lines`宣告外鍵，其中收貨行以複合外鍵（收貨行ID＋收貨ID，對應現有的`uq_gr_lines_id_gr`）保證該行確實屬於該收貨；採購單及採購行只存ID及單號快照，不宣告外鍵（收貨對採購單已有`RESTRICT`外鍵）。發票及付款對`suppliers`、`currencies`的外鍵令插入時取共享鎖，發生在採購單鎖之後，方向是採購單 → 供應商，與確認收貨相同（`GoodsReceiptPostingService.js:31`）；與Supplier管理「供應商 → 採購單」之間是既有的那條邊，沿用現行處理（InnoDB偵測死結，回409重試）。這一項沒有實測。
- **收貨清單**：建立發票頁用現有的`GET /api/v1/goods-receipts`列出`CONFIRMED`收貨，再以應付的端點標示哪些已在發票上（應收的同一做法）。現有清單沒有供應商篩選，回傳沒有幣別；需要Purchasing加`supplierId`篩選及回傳採購單的`currencyCode`（其負責人`9e2fd7ab`接受）。使用者須有`purchasing.view`。「已在發票上」的標示按頁批次讀取，只供顯示；是否可開票以建立草稿的交易內檢查為準。已知限制：清單不能只列「未開票」的收貨（那需要跨模組查詢），與應收相同。
- **前提**：首期沒有收貨沖銷入口。將來開放時，規則是「有未作廢、未取消應付發票的收貨不可沖銷」，由沖銷在採購單鎖下、碰庫存之前查應付；屬另一項改動，屆時連同釋放路徑一併重審。
