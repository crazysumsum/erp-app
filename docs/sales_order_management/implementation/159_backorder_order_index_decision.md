## Recommended exact change

Add exactly one nonunique visible ascending BTree to the existing Sales-owned active table:

```sql
ALTER TABLE sales_backorder_entries
  ADD INDEX idx_sales_backorder_order (sales_order_id,id),
  ALGORITHM=INPLACE, LOCK=NONE;
```

Use one new forward migration `server/database/migrations/*_add_sales_backorder_order_index.js`, with number allocated from fresh main together with the already-approved DEC043 migration after source initialization completes. The concrete private candidate is `PENDING_add_sales_backorder_order_index.js`: require the existing complete Backorder schema, distinguish a missing index from an incompatible named index, inspect exact two-column/nonunique/BTree/visible/ascending/no-prefix/no-expression shape, add once, then verify. A wrong existing definition fails without replacement or silent repair. Do not edit old migration0079, add/drop tables, change existing unique keys/FKs/triggers, add query hints, alter business commands, or touch archived indexes. Existing0070 inspection permits extra nonunique indexes while continuing to check original contracts; this must be verified natively rather than asserted as deployed compatibility.

The MySQL manual describes secondary index creation as an online, in-place operation with additional space/work; metadata locking can still wait on active transactions. The local migration will run serially after the initializer exits; native evidence must establish actual compatibility, duration, index bytes and unchanged rows/constraints. No production execution or zero-lock guarantee is granted. References: [online DDL](https://dev.mysql.com/doc/refman/26.7/en/innodb-online-ddl-operations.html), [metadata locks](https://dev.mysql.com/doc/refman/26.7/en/metadata-locking.html).
