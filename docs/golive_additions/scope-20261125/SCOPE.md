**跨模組的一條總規則**：每個命令先取來源模組的序列化點（出貨列或採購單列），再取本模組的列，最後才進Inventory；Inventory在自己的次序最後取成本池；呼叫方在Inventory返回之後不再取新的鎖。下面各節是這條規則的具體化。

## 5. 存貨成本（片C）

### 5.1 規則（r3重寫：取消「未計價數量」）

r2的「未計價數量」引出四個問題（Inventory `1b4b330e`、Codex TL `5a0a7789`）：計價數量可大於實物、混合部分退回的分攤、分倉估值高估、一般調整的沖銷。r3改為**一條不變式**：成本啟用後，每個SKU的池數量**永遠等於**該SKU全公司的實物數量（兩倉、所有狀態、在途）。所有改變數量的過帳都在同一交易寫成本，凡無法確定成本的過帳一律在Inventory寫入前拒絕，不猜、不記未計價。

- **成本池**：每個SKU一列，存數量及港幣帳面金額；單位成本＝金額÷數量，不另存。調撥、移位、狀態轉換（隔離↔可用）、預留及分配不動成本。
- **收貨**：入池金額＝實收基本數量×已鎖採購行單價÷採購單位換算因子，half-up到四位小數（`purchase_order_lines.unit_price`，已核`0113`）。應付改價不重估。
- **非港幣收貨**（TL裁定，Codex TL `5c40ccfc`）：成本功能啟用後仍可建立其他幣別的採購單及收貨草稿；確認時以已鎖採購單幣別為準，非HKD在Inventory過帳前整張拒絕（409），累收量、庫存及成本都不變；既有成功的重送取原結果。
- **出庫**（出貨、負調整、盤虧、退回供應商以外的出）：出池金額＝池金額×出庫數量÷池數量，half-up到四位小數；出庫數量等於池數量時取池內全部金額。因為池數量等於實物，出庫數量永遠不會大於池數量。
- **沖銷及退回按原值**（r5改寫，Codex TL `2dfe774b`、Inventory `0b6fc049`）：
  - 每個原異動的成本流水是「原值」（原數量Q、原金額V）。每次沖銷或退回分兩個數：**原值份額**及**實際變動**。
  - 原值份額用累計差額計：本次份額＝half-up(V×截至本次的累計回沖數量÷Q)−half-up(V×上次為止的累計回沖數量÷Q)。全部回沖時累計份額恰等於V，不會在最後一筆之前超出（例：Q=4、V=0.0002，逐件回沖的份額為0.0001、0.0000、0.0001、0.0000）。
  - 入的方向（出貨沖銷、客戶退貨收回、負調整的沖銷）：實際變動＝原值份額，加入池。
  - 出的方向（收貨沖銷、退回供應商、正調整的沖銷）：實際變動＝min(原值份額, 當時池金額)；若這一筆令池數量歸零，實際變動＝池內全部金額（不論多於或少於份額）。原值份額與實際變動的差額記在流水上（`original_value_hkd`為份額），供對帳。例（Codex TL）：池原有1件100，正調整入1件100，再收8件0元，出9件後池餘1件20；沖回那筆正調整時份額100，但這一筆令池數量歸零，實際出池20，差額80記錄在流水上，池不會變負。
  - 一般調整的沖銷（現有`inventoryReversalPosting.js:39–40,88–98`容許）用`ADJUSTMENT_IN_REVERSAL`、`ADJUSTMENT_OUT_REVERSAL`。移位及狀態轉換的沖銷不動成本。
- **原異動沒有成本流水**（成本啟用前過帳的單據）：其沖銷或退回被拒絕，訊息說明「原單在成本啟用前過帳，不能按原值回沖」，**而且在提交任何中間狀態之前拒絕**（r4，Fulfillment `691ba1a9`、PM `1620201e`）：
  - 出貨沖銷是兩個交易（Phase A寫`REVERSING`後提交，Phase B才進Inventory，`ShipmentReversalService.js:283,332–345`）；若到Phase B才被成本拒絕，Recovery只會退避、不會改回`SHIPPED`（`:135–147`），出貨會永久停在`REVERSING`。所以Inventory另提供一個同交易、只讀的檢查`assertIssueCostAvailableInTransaction(tx, { movementIds })`，Phase A在持出貨鎖、寫`REVERSING`之前呼叫；沒有成本流水或結果不明即拒絕（fail closed）。Phase B照樣按原值回沖並保留現有的租約及原子性核驗。
  - 收貨沖銷、客戶退貨收回、退回供應商都是單一交易，拒絕時整筆回滾，沒有中間狀態，不需另加預檢；由各自的Inventory provider在內部共用成本檢查（收貨沖銷及退回供應商驗原`RECEIPT`、客戶退貨驗原`ISSUE`），缺成本流水用同一錯誤，不要求呼叫方另用`ISSUE`專用入口（r5，Returns `ddae0200`）。出貨沖銷Phase A的預檢須逐一驗齊每個原`ISSUE`，並在before摘要記錄所驗的異動ID及當時的成本啟用狀態（Inventory `0b6fc049`）。
  - 正式環境按決定B在成本啟用後才做期初，所以不會出現；只影響測試及驗收資料庫。
- **正調整及盤盈**：池數量大於零時按當時池單位成本入池；池數量為零時按該SKU最近一筆成本流水的單位成本；該SKU從未有成本流水則該行須由操作者輸入單位成本（只在這種情況要求），否則拒絕。（見`DECISIONS.md`決定F。）
- **期初**：期初CSV加「單位成本（港幣）」，存在現有預檢紀錄的JSON內，不加資料欄（`inventory.md`）；期初過帳時每行寫一筆期初成本流水。財務須在期初結案前簽核兩倉的數量及金額。已在預檢完成但缺成本欄的期初工作須重新預檢（Inventory `1b4b330e`）。
- **啟用**（Inventory `1b4b330e` P2-6；r5補充，Codex TL `2dfe774b`、Inventory `0b6fc049`）：成本片的部署須先停止所有寫入、執行migration、只啟動含成本的版本，確認沒有舊版程序後才恢復；兩張表不齊或版本不符即停止寫入。停寫時若有出貨停在`REVERSING`，先以現行版本完成或由Recovery收尾，數目為零才可啟用；啟用命令檢查並在不為零時中止。
  - 已有庫存的環境（測試、驗收）以一次性初始化命令建立計價基線：每個有實物的SKU寫一筆`ENABLEMENT`流水（**不產生、不引用任何存貨異動**，`movement_id`為空），數量＝當時全公司實物，金額＝數量×財務CSV的單位成本；非正式環境可由部署設定明確容許以0成本初始化，正式環境不可。
  - 可安全重跑：每個SKU一個交易，鎖成本池列後若該SKU已有`ENABLEMENT`流水即略過；表上以唯一鍵保證每個SKU最多一筆。命令完成後逐SKU核對池數量等於實物、池金額等於流水合計，不符即報告並停止啟用，不寫半套。
  - 正式環境在成本啟用時沒有庫存（期初在其後），不需初始化。
  - 成本只在啟用之後完整：啟用前已過帳的出貨沒有出庫成本，初始化不會補上；毛利報表只計有成本流水的出貨行，其餘列為「成本未知」，報表註明成本啟用日。
- **分倉及批次估值**：池數量等於實物，所以各倉各批的估值＝實存數×SKU單位成本，四位小數；不按倉或批次篩選時，各行四捨五入後的合計與池金額的差額，在SKU小計列為「尾差」一行，SKU合計等於池金額；按倉或批次篩選時只顯示所選各行的值，不把其他倉、批次或在途的金額算作尾差（Inventory `0b6fc049`）。

### 5.2 鎖序

已核：Inventory所有改變數量的命令都經`InventoryLockService.lockForCommand`（倉庫 → 庫存控制列 → 庫位 → 庫位鎖 → 批次 → 結存 → 預留 → 調撥 → 盤點，`InventoryLockService.js:198–255`）；收貨新批次路徑另在其後以`lockBalancesAfterLot`鎖新結存（`InventoryPostingService.js:645,668`）。

裁定：**成本池列在Inventory該次呼叫的最後取得**——所有存貨鎖（含`lockBalancesAfterLot`）之後、寫異動之前——按`sku_id`升序，先插入不存在的列再`FOR UPDATE`，由一個共用函式做。不可放在`lockForCommand`內，否則收貨新批次路徑會變成「成本池 → 結存」，與其他命令相反。按SKU計（不分倉）令兩倉同一SKU的過帳在同一列上排隊，以20人規模接受。「最後」的意思是（r2改寫，Codex TL `22dd5f7e`）：取得成本池鎖之後，**不再取得任何可被他人競爭的既有業務列的新鎖**；對已鎖列的回寫、新列插入、追加歷史及稽核（例如`SalesFulfillmentService.js:444–447`）不算。由此：(1) 每個交易最多一次改變數量的Inventory呼叫（多行時合為一批）；(2) Inventory自己在存貨鎖之後的查驗，例如每個沖銷leg查原異動是否已被沖銷的`FOR SHARE`（`inventoryFulfillmentStock.js:186–188`），要全部在成本池鎖之前做完（Fulfillment `2af69ae9`）。Fulfillment已核對出貨沖銷Phase B只有一次數量批次（`2af69ae9`）；Inventory已核對期初、盤點及收貨各只有一次批次（`1b4b330e`）。盤點在成本池之前須完成現有的貨品、可用量及授權鎖（`InventoryStocktakeService.js:148–174,229–265`）及缺省結存的建立（`:275`、`:366–373`）；期初在實物過帳後才以鎖定讀取重驗使用者、權限及裝置（`InventoryOpeningService.js:118–141`），成本片須把這批鎖移到成本池之前，保留提交前驗證；收貨的事件重讀（`inventoryPurchaseReceipts.js:114–117`）只碰已取得的操作列。成本流水在異動ID確定後以有界批次追加。Purchasing及Returns各自核對自己的交易。本節只按來源閱讀，沒有執行。

## 6. 沖銷

### 6.1 出貨沖銷（片SR）

TL裁定已發（`993fb7da`）：只做「一律拒絕」版本。出貨的任一出貨行在未取消、未作廢的應收發票上（草稿或已確認：`ar_invoice_lines.active_shipment_line_id`不為NULL），或該出貨有任何未取消的客戶退貨單，即拒絕；任一方無法判定即拒絕。在Phase A持有`shipments`列`FOR UPDATE`之後查。現行`ShipmentReversalService.js`在Recovery（`:110`）及Phase B（`:278`）也呼叫下游檢查（Codex TL `22dd5f7e`）；改為不再重查佔用（REVERSING狀態已令應收開票及退貨建立被拒），其餘復原核驗保留。契約（r3，按Fulfillment分支`b9923152`的實作，`e7f7f9bf`）：跨程序的Recovery在已鎖的操作列下驗證Phase A持久記錄的provider登記版本；一般Phase B只接受同一服務實例由已提交的Phase A產生的私有綁定；Recovery接管後的Phase B接受Recovery確立的綁定。一般Phase B不另讀持久版本。Fulfillment的Phase A在READ COMMITTED下執行，持出貨鎖後的普通讀取已足夠；為與收貨一側一致，兩個provider仍對命中的佔用列做`FOR SHARE`（只鎖應收發票行及退貨行），結果不完整即拒絕。應收及退貨各提供一個在呼叫方交易內執行的只讀provider（`findShipmentInvoiceClaimsInTransaction`、`findShipmentReturnsInTransaction`）；應收建立及確認、退貨單建立都先鎖同一出貨列，應收取消及作廢只會減少佔用，所以普通讀取已足夠。公開route在兩個provider都註冊前不註冊；`NO_PROVIDER_REQUIRED`在應收已上線的部署不再成立。11-19裁定仍適用：沿用已合併的兩階段核心，**Recovery Job必須註冊**（這是背景工作；先前首期「不做背景工作」的原則對沖銷不適用）。成本由Inventory在其現有沖銷過帳內按原值回沖，Fulfillment不傳也不讀成本。這取代了應收SCOPE §3.1「首期不開放公開出貨沖銷」的前提；應收開票的鎖序不變。

### 6.2 收貨沖銷（片GR）

鎖序：操作列 → 採購單（`FOR UPDATE`）→ 採購行 → 收貨表頭 → 收貨明細 → **應付佔用檢查** → **數量上限檢查** → Inventory（含成本池）→ 寫更正單、收貨及採購單進度、稽核（`purchasing.md`，沿用採購設計§3.7、§4.12–4.13）。

- 應付佔用檢查：該收貨的任一收貨行在未取消、未作廢的應付發票上（`ap_invoice_lines.active_goods_receipt_line_id`不為NULL）即拒絕。**必須用鎖定讀取**（r3更正，Purchasing `e5cf48f1`）：收貨沖銷的交易是REPEATABLE READ（Inventory的收貨契約強制，`InventoryPurchaseContext.js:18–23`；`PurchasingOperationService.js:150–152`），快照在等採購單鎖之前已建立，持鎖後的普通讀取可能看不到剛提交的應付發票。所以應付提供的provider在採購單鎖之後，對命中的`ap_invoice_lines`列做`FOR SHARE`（只鎖發票行，不鎖發票或付款）；provider不存在、讀取失敗或結果不完整一律拒絕。應付取消及作廢先鎖發票再改發票行、不取採購單，所以這把共享鎖不會與它們成環。這是應付SCOPE r10 §3.1承諾「開放沖銷時連同釋放路徑一併重審」的結果：**釋放路徑不需改動**。貸項單不釋放佔用。
- 功能驗證須包含這個交錯（Codex TL `5a0a7789`）：沖銷先建立快照、等待採購單鎖，同時應付開票（或退回供應商過帳）持鎖並提交；之後沖銷必須看見它並拒絕或按上限計算。收貨沖銷與退回供應商兩種數量命令對同一收貨並行時，合計不超過實收。
- 已過帳退回量同樣用鎖定讀取：Returns提供的provider在採購單鎖之後對該收貨的退回行做`FOR SHARE`再加總，以退回行的`inventory_movement_id`不為NULL作為「已過帳」的證據（與退回單同一交易寫入），不JOIN未鎖的退回單表頭再按舊快照判斷（Purchasing `c1efc318`）；測試須包含「讀方等採購單鎖時，一張已存在的退回草稿被過帳並提交」；本次同一原明細的多行先合計再驗。
- 數量上限：每個收貨明細「已沖銷＋已過帳退回供應商＋本次 ≤ 實收」；收貨沖銷及退回供應商都在同一採購單鎖下檢查同一上限（`returns.md`的建議，採納）。同一收貨可以先後有沖銷及退回，只要合計不超過實收。
- 「應付未安裝」provider只在`ap_invoices`表不存在時可用；應付已上線的部署未註冊真實provider即啟動失敗。
- 鎖序補充：採購單 → 採購行 → 收貨表頭 → **收貨行 → 收貨明細**；更正單行在鎖下由已鎖的原收貨及明細建立（Inventory的`ownerProof`要求，`InventoryPurchaseContext.js:13–14,147–176`），不可預先建立；每次更正只呼叫一次Inventory；成本池在Inventory現有的`guard.check({locking:true})`（`inventoryPurchaseReversal.js:158`）及其他鎖定讀取之後才取。

## 7. 退貨、貸項單及退款

### 7.1 界線

退貨單（實物）、貸項單（金額）、退款（現金記錄）是各自過帳的單據，只以來源ID連結，**不自動產生**。銷售一側不加表，只讀連結（`sales.md`）。

### 7.2 客戶退貨

- 來源是一張`SHIPPED`的出貨單；可分多張退貨單。每行引用原發出明細`shipment_issue_details`（已核`0097`，其`inventory_movement_id`即原出貨異動），累計退回不超過原發出量。
- 鎖序：操作列 → 出貨列（`FOR UPDATE`，與應收開票及出貨沖銷同一點）→ 退貨單 → Inventory（收回入隔離區；成本按原出貨異動回入）→ 寫退貨單。退貨單草稿建立時同樣先鎖出貨列，所以出貨沖銷的Phase A能可靠地看到它。
- 隔離放行為可用：沿用Inventory現有的狀態轉換，不動成本。客戶退貨不改應收發票。

### 7.3 退回供應商

- 來源是一張已確認或部分沖銷（`PARTIALLY_REVERSED`）的收貨；每行引用原收貨明細，上限見6.2，同一原明細的多行先合計再驗；明細屬於該收貨、其採購行、SKU及原入庫異動，在採購單鎖下重驗。
- 鎖序：操作列 → 採購單（`FOR UPDATE`）→ 收貨表頭 → 收貨明細 → 退回單 → Inventory（出庫；成本按原收貨異動，5.1）→ 寫退回單。
- 已開應付發票的收貨**可以**退回供應商（業務退貨，不是更正）；金額由應付貸項單處理；退回不釋放應付佔用。應付發票仍按整張收貨的實收數量（應付r10，Sam已批准），不因先退回而減少；退回後若供應商發票已扣除退貨，入帳人員以改價或貸項對齊（見`DECISIONS.md`第3節）。
- 這取代了應付D8（按未佔用數量沖銷）：D8是為按數量開票設計的；整張開票下，沖銷一律被有效發票擋住，退回則不受發票影響。

### 7.4 貸項單（應收、應付對稱）

- 一張貸項單只對一張已確認的原發票，每行引用一個原發票行，每行一個金額，可附數量（只供顯示及退貨連結）。同一原發票行的已確認貸項累計不超過下文分派的行可貸上限；**同一原發票的已確認貸項總額累計不超過發票總額**（r3，Returns `ab5923ea`：兩行各10.0050、發票總額20.01，逐行到幣別小數位可得20.02；期初發票沒有行，更要靠整張上限），兩項都在確認時於原發票鎖下驗。可連結本側已過帳的退貨行：所連退貨行須屬於所連退貨單，而且其原出貨行（收貨明細）就是該原發票行的來源，由程式驗，不只靠外鍵。
- **期初發票**（應收G1、應付沒有）沒有發票行：只容許一行、不引用發票行的貸項；不計入按SKU的毛利（`apar.md`指出G1期初發票無原行）。
- 金額（r3改寫，Codex TL `5a0a7789`）：貸項行金額**只收幣別小數位**（不收四位小數），貸項單總額＝各行之和，不再四捨五入，所以多張貸項的合計就是各張之和，不會因每張各自進位而超出。上限有兩個，都在確認時於原發票鎖下驗：同一原發票行的已確認貸項累計不超過該行的「可貸上限」（r4，Returns `cbc61325`）：在原發票鎖下由不可變的行金額導出，以幣別最小單位計，各行先捨去，剩餘的單位按小數餘額由大至小、行號由小至大逐一分派，使各行上限之和恰等於發票總額（例：兩行各0.0149、總額0.03，上限為0.02及0.01），與確認先後無關；同一原發票的已確認貸項總額累計不超過發票總額（期初發票沒有行，只有這一個上限）。確認時同時重驗原發票仍為`CONFIRMED`。
- 確認時：以貸項金額沖減原發票未付額（不超過當時未付額），寫一筆對原發票的核銷（金額為0時不寫，不建立金額為0的核銷列）；其餘為貸項單的「可用額」，可核銷到同往來方、同幣別的其他已確認發票，或作退款。對原發票的那筆核銷不可單獨解除，只在作廢貸項單時一併撤銷。
- **發票表不加欄**（TL裁定，與`returns.md`建議的`credit_applied_amount`不同）：貸項的核銷與收款／付款的核銷同樣計入發票現有的`allocated_amount`，所以`outstanding_amount = total_amount − allocated_amount`的`CHECK`、帳齡、Business Master及Supplier的未付檢查、發票作廢「須先解除全部核銷」的規則都不變，已合併的收款／付款程式不用改。代價：發票的`allocated_amount`不再只代表現金；發票詳情及報表須分別列出兩種核銷（各有自己的表，可分辨）。已核：main的應收發票詳情及應付發票詳情（`62fd35f7`）都把這一欄標為「已核銷」而不是「已收／已付」，發票列印（G5）不顯示它；`codex-erp-app-apar-01`須確認沒有其他地方把它當作現金。
- 鎖序：建立草稿：操作列 → 原發票（`FOR UPDATE`，驗累計上限）→ 插入。確認：操作列 → 貸項單 → 原發票 → 核銷 → 編號。核銷到其他發票：貸項單 → 發票（ID升序）→ 核銷。（r2更正，apar-01 `a96ceec8`：現金核銷的次序兩側不同——應收是事件 → 發票（ID升序）→ 收款 → 核銷（`ArReceiptService.js:88–94,126–128`），應付是事件 → 付款 → 發票（ID升序）→ 核銷（`62fd35f7`的`ApPaymentService.js:93–96,130–134`）。）貸項的命令不取收款或付款的鎖，現金的命令不取貸項單的鎖，所以兩族之間沒有共同的第二把鎖，不會互相等待；也沒有任何命令先鎖發票再鎖貸項單。確認時讀同一原發票行的其他已確認貸項，用普通讀取：所有確認都先鎖同一原發票，已經序列化，不另用鎖定讀取以免造成倒序。作廢貸項單：須沒有對其他發票的有效核銷及有效退款；鎖貸項單 → 原發票，撤銷對原發票的核銷。原發票作廢：除現行的`allocated_amount`須為0外，**另須沒有已確認的貸項單以它為原發票**（r3，Returns `ab5923ea`：原發票已由現金收清時，貸項對原發票的沖減為0，解除現金核銷後`allocated_amount`回到0，但貸項及其退款仍然有效）。在原發票鎖下以普通讀取查（所有貸項確認都先鎖原發票，已序列化），沿用原錯誤碼。
- 查詢：發票詳情API現有的`allocations`維持只列現金核銷，另加`creditAllocations`，兩者在同一讀取內回傳（apar-01 `a96ceec8`）。發票作廢被拒時，現有錯誤碼`AR_INVOICE_HAS_ALLOCATIONS`／應付對應碼不變，訊息須同時提示「先解除收款／付款核銷，或先作廢貸項單」。
- 幣別影響檢查：兩側`BusinessMasterImpactChecker`把草稿貸項、可用額大於0的已確認貸項及草稿退款算作「進行中」，令該幣別不可停用。
- 供應商或客戶被停用、封存後，既有貸項照樣可核銷、退款或作廢（與應付r10「清償既有債務不受往來方狀態影響」同一原則）；不新建貸項的限制只按原發票，不另驗往來方狀態。
- 現有表須改的只有兩類`CHECK`：應收／應付編號表的文件種類加`CREDIT_NOTE`、`REFUND`；操作記錄表的對象類型加`CREDIT_NOTE`、`CREDIT_APPLICATION`、`REFUND`（已核`0123:34,225`；應付`62fd35f7`的`0129:31,240`）。不改資料，不加欄。
- 這實現了應付D5及應收r3的「依原發票行沖減、超額成同幣別貸項餘額」；不做r3的出貨來源分配及沖銷證明。

### 7.5 退款記錄

- 客戶退款：從應收貸項單的可用額付出；供應商退款：從應付貸項單的可用額收回。只記錄（日期、金額、方式、參考號），不產生銀行檔。
- 來源只限貸項單。未核銷收款的退款屬預收款，第二期（Sam）；應付付款未核銷額由供應商退回，本輪不做（付款記錯可作廢）。
- 鎖序：操作列 → 貸項單 → 退款 → 編號。作廢退款：可用額加回。

## 10. 待補

- 交付次序：退貨片（RT）的表須先於應收及應付貸項片（ARC、APC）合併，因為貸項單及貸項行對退貨單及退貨行有外鍵；程式可並行寫（Returns `ab5923ea`）。
- 客戶退貨的Inventory接口（r3，Returns `ab5923ea`）：現有`postCustomerReturnReceiptInTransaction`只過單一SKU、批次及庫位，並會拒絕過期及不足最低入庫效期的貨（`InventoryPostingService.js:359,604–678,629,792–804`）。由Inventory另提供客戶退貨及退回供應商各一個批次provider，帶原異動ID；退回的貨一律收入隔離區，不因效期拒收（貨已在客戶手上，拒收只會令實物與帳不符），放行為可用時沿用現有的放行檢查（含效期）。授權照收貨的做法由呼叫模組的上下文證明：provider驗證呼叫方交易內已鎖的退貨單及操作者在當下持有退貨片新seed的`returns.customer.mgmt`或`returns.supplier.mgmt`，不依賴目前只有消費者、沒有目錄及seed的`returns.operation`。
- `supplier.md`（已交）：Supplier一側0人日。退回供應商、應付貸項及退款都沿原收貨或原發票追溯到供應商，現有的採購單及應付引用檢查已鎖定供應商代碼並擋永久刪除。封存規則不變（只有未完成採購單及未付的已確認應付發票擋封存）；有未完成的退回單、貸項草稿或貸項可用額的供應商仍可封存，之後照樣可以完成或作廢這些單據（與應付r10「清償既有債務不受供應商狀態影響」同一原則）。
